# M4 否决项② — 控制端点 accept 瞬时错误即永久失效 · 修复证据

> 日期：2026-09-27。范围：**M4 收口执行清单 §6 #1**（用户 2026-09-26 已批准：修端点缺陷）。
> 结论：**修复完成**——规则单测 **RED→GREEN**；真实主机端点经 RST 风暴前后共 24 次 `GET /v1/retry/status` **全程 200（PASS）**。
> **诚实边界**：本轮 HIL **未能**在受控条件下复现出原始 accept 瞬时错误；`continue` 分支由**单测**锁定，非 HIL 触发（见 §5）。另发现一处**独立**健壮性缺口（见 §5.2，待裁定，本轮未改）。

## 1. 缺陷与根因

- **症状（2026-09-26 实测，见 `M4收口就绪核查.md` §5.1）**：`state_host` 控制端点（`127.0.0.1:45910`）曾 `bind` 成功，其后 `GET /v1/retry/status` 一律"无法连接"；`netstat` 仅见 **TIME_WAIT、无 LISTENING** → **监听套接字消失**；托盘"重试识别/重试填入"因此失败（M4 否决项②）。
- **根因**：`host/src/state_host.cpp` 的 `http_thread` accept 循环，在**无停止请求**时唯一可退出路径是 `accept()` 返回 `INVALID_SOCKET`（`g_http_stop` 全仓**从未被写入**，`InterlockedCompareExchange(&g_http_stop,0,0)` 恒为 0）。旧实现 `if (c == INVALID_SOCKET) break;` 把**任何** accept 错误都当终止 → 一次瞬时错误即 `closesocket(s); WSACleanup();`，端点**永久失效**且无重绑、无日志。

## 4. 真实主机端点行为验证（C/H）

**脚本**：`tools/host_accept_resilience.ps1`（**可复跑**）。

**结果（2026-09-27 实测）**：

## 5. 残余风险与诚实边界

### 5.1 未复现原始瞬时错误
800 次 RST 风暴**未**令 `accept()` 返回错误（Windows 对本机已 RST 的 backlog 连接通常仍返回可用套接字，随后的 `recv` 才报错并被 `http_handle_conn` 的 `n<=0` 分支正常处理）。因此 accept 的 **`continue` 分支在本轮 HIL 未被真实触发**；其正确性由 §3 单测 + 代码审查保证。原缺陷的触发条件（哪种 Winsock 瞬时错误）未能确定性构造。

### 5.2 【独立缺口 —— **已于 2026-09-27 修复，见 §8**】单线程阻塞 recv 可被"连上不发"的连接拖死
诱导脚本 `tools/induce_accept_transient.ps1` 的实测（netstat 逐步抓取）显示：
- 控制端点为**单线程串行 accept**，`http_handle_conn` 的 `recv()` **无超时**；
- 一条"连上但从不发数据/不关闭"的连接被 accept 后，`recv` **永久阻塞** → accept 循环**停摆**；
- 此时端点 **仍在 `LISTENING`**，但**不再响应**（新连接超时；`listen(s,4)` backlog 满后新 SYN 被拒），直到该连接关闭；
- **与原始缺陷的区别**：原始缺陷＝监听套接字**消失**（netstat 无 LISTENING）；此为**监听套接字尚在但 accept 停摆**。两者机制不同。
- **影响面**：控制端点仅 `127.0.0.1`，客户端为本机托盘 / 启动器；现实触发＝本机客户端异常停滞。
- **是否修复**（如 `SO_RCVTIMEO` 设收包超时 / 每连接并发处理 / `select` 超时）**待用户裁定**；本轮**未改**（不属已批准清单 #1、#2、#3、#4，避免顺手扩范围）。

## 6. 结论
- 已批准执行清单 **§6 #1 完成**：端点不再因 accept 瞬时错误永久失效；规则被单测锁定。
- **§5.2 缺口已修复**（2026-09-27，用户确认；采用 Oracle 推荐 `SO_RCVTIMEO`）：停顿连接在 ~5s 内被释放，端点自行恢复；RED→GREEN 见 §8。

## 7. 独立复核（Oracle，2026-09-27，只读）

对本次修复与 §5.2 发现做独立复核，结论如下（已据其修正本修复）：

- **分类正确性**：`WSAECONNRESET` 由 `accept()` 返回是 Windows **确有且已知**的行为（现代 Linux 会静默丢弃被中止的待接入连接，Windows 会显式报错），故"记录并继续"正确；`WSAEINTR/WSAEWOULDBLOCK` 在本设计下实为不可达（防御性保留，无害）。
- **【已采纳·修正】**：`WSAENETDOWN` 原落 default=瞬时 → 若 Winsock 栈已死，会以 ~20 Hz **永久重试+刷日志**且端点静默不可用（与原始症状同类）。**已补入致命集**（见 §2/§3），并补断言 RED→GREEN。
- **测试有效性（已核）**：复核提示"测试可能误用 `errno.h` 的 `ECONNRESET`(104) 而非 `WSAECONNRESET`(10054)"；经核对，本测试**全部使用 `WSAE*` 常量**（无裸 errno），该隐患不成立。
- **§5.2 缺口（复核判定：真实、严重度较高、宜修）**：单线程 + 阻塞 `recv`（无超时）确会被"连上不发"的本地客户端拖死；**推荐最小修法**＝accept 后设 `SO_RCVTIMEO`（Windows 为 **`DWORD` 毫秒**，非 `timeval`）：`DWORD t=5000; setsockopt(c,SOL_SOCKET,SO_RCVTIMEO,(char*)&t,sizeof(t));`（可选再加 `SO_SNDTIMEO`）；每连接并发/`select` 属过度设计。**本轮未改（不在已批准清单，待用户裁定）。**
- **其余**：`Sleep(50)`+continue 合理（非空转；不需在循环内重绑，重绑会引入端口/TIME_WAIT 复杂性，宜由进程级重启兜底）；`g_http_stop` 全仓只读、无优雅停机路径——属现状设计，若日后加停机，注意 Windows 下**跨线程 `closesocket()` 不能可靠唤醒阻塞在 `accept()` 的线程**。
